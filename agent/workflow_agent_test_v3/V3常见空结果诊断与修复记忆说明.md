# V3 常见空结果诊断与修复记忆说明

本文记录本轮“常见空结果诊断、有限修复、成功修复记忆”的实现及使用边界。依据是项目根 `AGENTS.md` 和当前 `dc_agent` 源码，不把历史模型回答、规则库覆盖率或离线测试数量当作本次源文件事实。

当前工作流仍为：2229 造路径 → 2442/8448 查询并整理本次 GZK → 外部框架接入 → 4912 动态执行 → 原后半链。平台由用户亲自配置；**7882 单位换算不前移，4912 和后半链本轮不需要修改。** 接入节点使用本轮更新后的完整脚本，保留现场的服务 URL、令牌和原有 14 个 `agent` 子字段。

## 1. 本轮要解决什么

“最终没有数据”可能发生在不同环节。以前只有 `ready` 或空数组，不能说明究竟是规则没有查到、原文件没有数据、代码漏提取、日期没有绑定，还是后半链的筛选条件没有满足。本轮将这些情况区分，并只对真实源支持的代码问题做有限修复。

| 情况 | 当前处理 | 是否启动生成或修复 |
|---|---|---|
| 本次 `GZKJG` 为空或没有有效规则名称 | 精确错误码 `without_GZKJG` | 不提交生成、不进入任务队列 |
| 原始文件粗审明确为 `no_data` | 保留既有 `FilenoData` | 不进入设计和代码生成 |
| 源文件可能有数据，但本机运行生成代码得到空 `ExcelData` | 记录 `empty_extraction` 问题，回查源与代码 | 使用现有修复预算；仍为空且无可交付候选时返回 `EMPTY_EXTRACTION` |
| `end_date` 缺失，当前源或允许使用的本次标题提供可核对期间 | 记录 `end_date_empty`，修复定位、正则或期间绑定 | 使用现有修复预算；只剩这类已知日期问题且无可交付候选时返回 `END_DATE_EMPTY` |
| `end_date` 缺失，仍无可靠统计期间 | 日期留空，报告 warning 和下游风险 | 不为通过验证补造日期 |
| 源单位与 GZK/库表单位不同，但源单位提取正确 | 归类 `unit_conversion`，作为建议项放过 | 不改解析器、不在外部框架换算；交给原工作流 4551/7882 |
| 名称与 GZK 未匹配、规则编码缺失 | 给出本机下游可用性估计 | 不能单凭匹配数证明解析器错误或反向造名 |

这些诊断均沿用 Python 正式接口 `main(params) → code/msg/ExcelData`；每条记录仍是 `indicator_name`、`indicator_data`、`indicator_unit`、`end_date` 四核心字段。没有新增 TXT/JSON 输入链路，也没有要求生产解析器在运行时读取 GZK。

## 2. 空 GZK：先返回 `without_GZKJG`

### 2.1 平台接入节点的本地短路

更新后的 `工作流节点代码/外部框架接入.py` 会在 HTTP 调用前检查 `GZKJG`。在其他业务参数合法的前提下，以下情况进入无有效规则分支：缺少/为 `None`、空数组、表示空数组或 `null` 的合法 JSON 字符串，以及数组中所有 `rule_indicator_name` 都为空白、`empty`、`null`、`none` 或不具有有效文本名称。

本地返回仍为 `{"agent": [唯一对象]}`，14 个子字段全部为 String，关键内容是：

| 字段 | 本地无规则时的内容 |
|---|---|
| `status` | `invalid_input` |
| `stage` | `preflight_rules` |
| `error_code` | `without_GZKJG`，大小写和下划线保持精确 |
| `message` | 提示检查本次规则查询与入参映射，说明没有调用外部生成服务 |
| `elapsed_seconds` | `0.00` |
| `job_id` | 空字符串，因为没有受理外部任务 |
| `PythonFile/PythonCode/code_sha256/artifact_version` | 全部为空，禁止残留上一次代码 |
| 其余 String 字段 | 没有实际值时为空 |

这一路不建立 HTTP 会话，也不调用模型。接入节点正常写回诊断，4912 再按现有严格状态检查拒绝 `invalid_input`，阻止后半链继续使用无效代码。

若只有部分规则名称为空，其他行有效，则保留原数组交给服务端 `Task` 清理并记录 `invalid_rule_rows`。8448 按各列最长长度生成对象，尾部可能出现空名称，不能因此阻断整批有效规则。

`False`、数字、字典、非法 JSON 字符串等结构错误仍应按真实入参错误报告；不能把布尔假值自动当成空数组，更不能静默补一份旧 GZK。

### 2.2 HTTP 和命令行入口的同一业务含义

服务端 `Task.filter_invalid_names()` 也使用专用验证错误类型 `without_GZKJG`。HTTP 接口先完成 `ExcelJobRequest.task_payload()` 验证，再调用 `JobStore.submit()`；因此无有效规则的请求会得到 **HTTP 422 + `error_code=without_GZKJG`**，不会写入生成任务队列，也不会为此触发预检、设计或生成。

HTTP 422 是入参诊断对象，和平台节点本地返回的 14 字段 `agent` 是两个不同边界。若绕过本地检查直接请求服务端，接入节点会在异常中显示经过限制的错误码、字段位置和诊断编号；它不会把任意响应正文或被拒绝的实际输入原样写到平台日志。HTTP 诊断文件位于 `runtime/diagnostics/http-input-errors/<diagnostic_id>.json`。

排查顺序应是：确认当前测试的 `pageTitle` → 检查 2442 查询条件、规则路由及 8448 实际返回 → 检查接入参数 `GZKJG` 是否绑定 `GZK.GZKJG` → 确认更新后的脚本和服务已实际加载。不要为绕过 `without_GZKJG` 伪造规则或修改正确解析器。

## 3. 原始源无数据，与代码提取为空分开处理

### 3.1 真实源粗审：保留 `FilenoData`

原有 `ContentPreflight` 在实际下载、读取和完整检查源文件后，依据全部 Sheet/表格内容做粗审。明确没有业务数据时返回 `no_data`，由 `application/preflight.py` 抛出 `FilenoData`，保存 `preflight.json` 及实际原因，停止后续代码生成。

零、负数和数值字符串有效。只有日期、单位、目录、表头、空格或横线等不能冒充业务记录；单位或日期缺失本身也不表示没有业务数据。格式复杂、合并表头、公式缓存不明等不应直接当成无数据，`uncertain` 会继续后续流程。格式损坏或读取上限问题仍按实际读取错误处理，不能统一改成 `FilenoData`。

这是原来已有的源内容粗审，本轮没有额外加一次同类模型调用。

### 3.2 生成代码本机执行为空：进入现有有限修复

`validation/validator.py` 实际运行候选代码，使用本次下载的原始 bytes mock 下载接口。若返回成功码但 `ExcelData=[]`，`runtime_contract` 会失败，并带上 `category=empty_extraction`、解析器返回码和记录数。`msg` 会进入受限的验证反馈，帮助定位选错 Sheet、过滤条件过强、提前 return 或输出键错误等原因。

修复不能把“程序没有抽到数据”解释成“文件没有数据”。下一轮仍应检查：

- 实际容器格式与读取方式，包括 gzip 包装、编码、XLS/XLSX magic。
- 全部 Sheet/表块是否真正扫描，空 Sheet、目录和纯说明如何排除。
- 合并表头、空行、列选择、数值清洗与无效值判定是否过度过滤。
- 原始 `.xls` 的日期、年份等表头 `ctype` 和 Python 类型；整数语义浮点年份不能因正则只接受整数字符串而全部漏掉。
- 零值、负数和原始精度是否被保留，实际下载接口与返回契约是否正确。

上述内容是修复策略和检查方向，不能替代对当前文件的直接核对。修复代码必须重新执行本次源 bytes，不能生成一批看似合理的示例记录，也不能从过去成功案例抄值。

若现有修复轮数、停滞条件或时间预算已耗尽，仍是 `code=0` 的空提取且没有可交付候选，错误为 `EMPTY_EXTRACTION`，服务结果进入 `review_required`。一般运行失败、错误返回码、返回结构错误等仍可能是 `VALIDATION_FAILED` 或相应运行错误，不能把所有失败都改称空提取。

## 4. 日期缺失：先找来源，再决定是否修复

### 4.1 四种信息必须分清

修复时要分别确认：实际日期来源位置、统计期间、对应记录/数据列的绑定关系、归一后的截止日期。标题写着某月，不代表每一列都属于该月；表内行名或表头中的季度、上半年、累计月份等明确期间，应按实际记录绑定。

表内期间优先。只有表内没有可靠统计期且当前规则/profile 允许，才使用本次运行时 `title`。编制日期、发布时间 `publictime`、下载日期、当前日期以及历史样本标题都不能替代统计截止日期。日期来自 `title` 时，生成代码开头仍要注明，并动态读取本次字段、计算期末。

### 4.2 机械检查识别“可回查修复”与“仍未知”

`validation/readiness.py` 的 `end_date_presence` 识别 `None`、空字符串和 `empty/null/none` 等缺失表现。四字段契约另外要求正式 `end_date` 为字符串；未知日期应由解析器输出空字符串，不能用不合法类型绕过契约。

机械检查逐条核对记录自己的 `date_refs`。设计中的 `date_position` 保留为审查线索，不把同 Sheet 或其他表块的日期广播到缺日期记录。仅在单一有内容的 Sheet、源中没有明确期间线索或其他记录日期绑定，且标题包含唯一明确年月时，才启用隐式标题回查；已有明确本地期间的记录不被外部标题覆盖。

| 当前证据状态 | `end_date_presence` | 处理原则 |
|---|---|---|
| 缺日期，且发现当前源位置或允许的标题期间线索 | fail | 进入有限修复，回查日期读取、正则转义、传播和逐列绑定 |
| 缺日期，仍未建立可靠来源 | warning | 日期留空，记录未解决与下游可能清除的风险 |
| 日期不缺失 | pass | 仍需通过格式、源证据及语义检查，不代表日期一定正确 |

“有一个 ref 或标题线索”只是启动回查的机械信号，不自动证明它就是当前指标的统计期间。最终还需源事实和语义审查确认。没有可靠来源时，不能为把 warning 改成 pass 而填写一个日期。

`details.record_indices` 只列可回查修复的缺失记录，`unknown_record_indices` 另列仍未知的记录。两种情况并存时，失败仅针对前者，后者继续保留警告；不会因为另一 Sheet 有日期就要求给未知记录填同一个日期。

当设计明确绑定 `runtime:title`，或记录证据实际引用它时，还有相应的一致性检查。当前公共辅助函数 `title_month_end()` 只对**唯一明确的年月**计算月末；季度、半年、全年等不由该函数猜成月份。其他周期必须由当前源和专用解析逻辑确定，不能声称已由这一个辅助函数统一解决。

### 4.3 修复日期时保护其余字段

典型可修复问题包括：正则多做一层反斜杠转义、读取了错误标题变量、日期已算出却没有写入记录、多个期间列绑定到同一个日期、将发布日期当统计期等。修复计划为 `end_date_empty` 时，默认只允许修改相关记录的 `end_date`；名称、数值、单位、下载接口和无关逻辑应保留。

若现有预算耗尽、没有可交付候选，而且失败类别只剩已知的 `end_date_empty`，返回 `END_DATE_EMPTY` 并进入 `review_required`。若仍混有其他缺陷，则通常是更一般的验证失败，具体看保存的验证报告。若日期无可靠来源而只是 warning，则不应硬报成“已知日期修复失败”，也不应伪造日期来提高下游数量。

## 5. 单位差异继续交给原工作流

本轮将两种情况明确区分：

1. **源表本来用“万元”，库表要求另一单位，解析器忠实输出源值和源单位。** 这属于 `unit_conversion`，仅作建议项，不是代码正确性缺陷。纯粹此类差异、且引用和其他检查合法时，不触发代码修复，也不让外部模型修改源数值。4551/7882 继续负责公司工作流原有换算职责。
2. **源表明明是百分比、吨等，解析器错误继承了另一表块的“万元”。** 这属于 `source_unit` 或真实源绑定缺陷，需要根据当前源修正。不能因为库表最后可能换算，就放过错误提取。

没有有效源单位时按项目规则输出 `-`；不能仅因名称包含“率”“指数”或为了匹配库表而推断单位。名称括号中的单位提取后，括号及内容仍保留在 `indicator_name` 中。本轮不前移 7882、不新增外部换算、不去重、不四舍五入。

## 6. 本机下游可用性估计能说明什么

`downstream_readiness` 按当前记录和 GZK 估算：

- 名称去首尾空白后命中的记录数 `name_matches`。
- 命中规则具有有效编码的记录数 `coded_records`。
- 同时具有合法日期的记录数 `dated_records`。

结果原因可为 `NO_NAME_MATCH`、`MISSING_RULE_CODE`、`END_DATE_EMPTY`、`READY`。没有估计可用记录时给 warning，帮助解释为什么后续可能没有输出。

这只是本机估计，不会过滤 `ExcelData`、补规则编码、修改名称或转换单位，**没有接收 DC 后半链的执行回传**。即使估计为 `READY`，也不能等同于平台实际 `out_data` 正确；估计为零，也不能单凭它把正确源名称改成 GZK 名称。应继续回查规则覆盖、映射、部署版本和平台日志。

## 7. 修复从整段重写改为逐问题跟踪

新增 `repair/session.py` 管理一个任务内的问题账本和修复上下文。它复用原有生成、执行、语义审查流程，不再额外调用模型做一轮“修复总结”。

### 7.1 每个问题有稳定编号和证据

每条问题包含 `issue_id`、类别、检查名、首次/最近出现轮次、受影响记录、`data_refs/source_refs`、涉及函数、候选代码 hash、观察历史和解决历史。编号按问题类别、检查与源数据位置等计算，不使用“第几条回复”作为唯一身份。

状态含 `open`、`validated`、`resolved`、`advisory`。机械通过和语义认可分开保存：代码运行通过可能将问题标为 `validated`；它不会仅因为下一轮模型说“已解决”就直接成为已验证成功经验。

恢复已有任务时，只有 policy、源 SHA256 和本次输入 hash 一致，才恢复相同问题账本，防止将另一文件、另一输入或另一策略的问题状态套到本次任务。

### 7.2 下一轮收到受限、具体的修复上下文

`RepairSession.plan()` 聚合当前未解决问题，优先处理空提取、运行问题和日期缺失，提供：

- 本轮目标问题及原候选 hash。
- 受影响记录与逐条源引用。
- 当前真实源中的精确单元格、相邻行及顶部表头片段；如实际引用标题，则包含本次 `runtime:title`。
- 相关函数及行号的代码片段；已有函数定位时优先使用定位，没有时提供 `main/_dc_validate` 和可能的日期函数。
- 适用修复策略及符合范围的已验证经验。

这些片段有长度上限，完整材料仍保存在任务目录。提示要求合并共同根因，只修当前源支持的问题，保留无关输出和函数；不能为了 GZK 命中数重造指标名称。

### 7.3 保护字段与函数差异检查

`RepairSession.guard()` 在实际重新执行后，按保留的源 `data_ref` 对比修复前后记录：日期问题只放开日期，名称问题只放开名称，数值问题只放开数值，源单位问题只放开单位；`unit_conversion` 不开放任何字段供换算。被保护字段发生计划外变化，会产生 `repair_regression` 失败。

数值比较允许等价数值表示，例如零的数字与数值字符串，不会要求为了测试通过把所有数值转成 float；源精度仍须保留。

代码层面还计算 AST 函数/模块差异，并写 `repair-diff-N.json`。当本轮问题都提供明确代码范围时，改动范围外的已有函数、全局赋值、模块行为语句或既有 import 会触发 `repair_code_scope` 失败；新增必要 helper/import 可以存在。这样可拦住“零值样本输出没变，但数值倍率常量被误改”的问题。没有完整代码定位时仍记录差异，但不能宣称已严格证明全部无关代码完全未动。

保护检查面向仍然保留、能按源引用对应的记录。丢失源引用仍按覆盖问题记录，当前覆盖策略为建议项；它不是对所有历史遗漏和全部业务逻辑的完整回归证明。

每个修复候选同时保存 `repair-baseline-N.json`，包含完整基线候选、报告、修复计划，以及源、输入、策略和上下文指纹。恢复任务时，历史候选和最新候选都必须重放原保护检查；不能因为 `--resume-candidate` 就绕过上次拒绝。若已拒绝候选的保护基线丢失，则明确拒绝该恢复操作，要求重新构建。

### 7.4 逐问题验收与最终候选选择

每次修复后都再次本机执行原始 bytes，检查正式/证据入口一致、四字段、源值与引用、日期及计划外变化，再进入原有语义审查。`Review` 增加结构化 `issues`、`resolved_issue_ids`；新问题不能藏在一句“通过”后，已解决问题要按编号复核。

全部机械问题闭环前都要确认原受影响 `data_ref` 和记录计数仍然接受验证。删除出错记录可以形成覆盖告警，但不能标记为修复成功。每个新代码 hash 都要重新绑定机械验收；已经在上一候选上 `validated/resolved` 不表示修改后的候选自动继承。尚未完成逐项验收的问题保留在 `repair_issue_status` 告警中。

模型可以补充 `repair_lessons`，按问题编号说明 `root_cause`、`fix_summary` 和 `applicability`。这段自然语言只解释根因、修复机制和适用条件，提示明确要求不复制样本值、日期、标题、名称或整段旧代码。模型声明本身不能代替机械验收与源证据。

候选池仍保留先前机械可用版本，后续修复失败时可按既有策略回退，并明确质量告警。`ready` 只说明有代码可交付；`usable_with_warnings` 不表示所有语义问题已解决。最终选中的代码与问题验收记录不一致时，不能把另一轮的修复写成当前版本的成功经验。

## 8. 记忆保存什么、什么时候使用

### 8.1 成功经验有独立的 SQLite 存储

`repair/memory.py` 使用 `runtime/repair_memory/verified_cases.sqlite`，表为 `verified_cases`。它保存策略 ID、问题类别、来源范围、策略范围、任务与源 hash、修复前后代码 hash、验证检查及可选的根因说明。

当前只有满足以下条件的已解决问题，才由 `RepairSession.finish()` 晋升为成功经验：

1. 最终选中候选的 `semantic_status=accepted`。
2. 该问题的验收 hash 与最终选中代码完全一致。
3. 解决方式是 `execution_and_semantic_review`，包括本机执行、源证据与语义认可；仅靠 `resolved_issue_ids` 的口头关闭不够。
4. 验证检查包含 `runtime_contract`、`source_evidence`、`model_semantic_review`，修复前后代码 hash 不同。
5. 当前自动晋升类别限于 `empty_extraction`、`end_date_empty`、`runtime`、`source_value`。

模块还提供 `name_semantics`、`source_unit` 的人工整理策略，供定位问题时参考；当前实现没有将这两类自动晋升为成功记忆。失败尝试、未验证修复、语义未接受或未完成的回退版本不会因“本轮结束”就自动变成成功案例。某个问题已逐项验证时，其他未解决的建议项不抹除这条修复经验，但它也不表示整份代码已全部正确。

### 8.2 检索范围与历史事实隔离

历史案例按同一 `pageTitle + fileType` 形成的 `source_key`、问题类别及 `policy_key` 检索。当前 `policy_key` 纳入修复策略、任务链路、Skill hash 和 profile hash；Skill/profile 变化后，不会把旧策略范围的成功案例直接混入。

每类只取有限的最近案例，返回受控策略 ID、已通过检查、案例编号和 `has_auditable_lesson` 标记。旧代码、旧输出、旧标题、旧数值、旧日期、旧源片段和自由文本 lesson 都不由记忆检索器送入新任务的运行 prompt。

lesson 是模型撰写的根因说明，保存在问题审查记录和 SQLite 供人员复核，不直接重放给新任务。即使提示模型用抽象方式写作，长度约束也不能保证其中完全没有旧事实。未来将它提升为新技能前，还需单独做事实抽象审查和固定样本回归；当前运行阶段仅复用已经整理的受控策略和验证标记。历史经验不能证明本次指标名称、数值、单位或日期是什么。

这属于**任务外部记忆与经验检索**：不修改模型权重，不自动训练模型，不自动改写全局 Skill。SQLite 不可读写时记录 warning，继续使用当前源验证与已整理策略，不用未验证内容顶替成功经验。

## 10. 平台更新、缓存和验证边界

### 10.1 用户需要更新的内容

用户将当前 `外部框架接入.py` 的完整正文更新到平台接入节点，并保留现场正确的 `API_BASE_URL`、`API_TOKEN`、六项业务输入映射及可选稳定运行 ID。`agent` 继续为恰好一条记录的 Array<Object>，原有 14 个 String 子字段、父变量映射不变；4912 和后半链无需因本轮需求修改。

服务进程需实际加载更新后的本机代码，不能只改磁盘文件却继续测旧进程。接入节点或服务版本没有更新时，仍可能看到旧错误文案或旧行为。平台更新和 DC 实际验收由用户亲自执行，本轮说明不代表已经代替用户部署。

### 10.2 当前缓存策略保留

原有资产命中继续复用原版本，不会为了本轮新增检查自动重生成、自动重跑全套粗审或改写正式生产资产。新增修复账本、缺失诊断和记忆链路主要适用于**新生成，或经过明确操作的重建任务**。

显式 `rebuild=True`/相应命令行重建属于独立操作；不能把“多点几次平台重试”解释成要求重建。现有 API 的稳定输入幂等仍可能取回同一任务和同一代码。验证本轮修复链时，应明确测试的是生成/重建分支还是已有资产缓存分支，记录代码版本和 SHA256，避免把旧资产命中当成新修复已执行。

### 10.3 预算与调用不扩张

当前本机 API 总预算仍为 360 秒，生成侧使用原有预算与修复轮数、质量修复和停滞约束。本轮复用已有 design/generate/review 调用，在其上下文和 schema 中加入修复计划与 lesson；没有额外新增记忆学习、总结或空结果分类专用模型调用，也没有为此增加配置的轮数/时间上限。

平台单次尝试与重试仍受实际工作流配置约束。超时、提供方中断或无进展时，按既有候选保留策略选取可用版本并报告告警；没有可用版本则明确失败。不能承诺 360 秒内所有复杂源都能修好，更不能为满足预算放过造值或造日期。

### 10.4 本轮验证如何阅读

本轮未修改 `.env`、规则工作簿或生产资产，未调用真实模型，也未进行真实 DC 工作流验收。最终全量 **451 项通过，85.76 秒**；`ruff check src tests` 与 `ruff format --check src tests` 通过。正式报告为 [v3-repair-final.xml](../runtime/diagnostics/v3-repair-final.xml)。执行使用用户已有 dc Python 环境：

```powershell
python -m pytest -q --basetemp=runtime/test_runs/v3-repair-final --junitxml=runtime/diagnostics/v3-repair-final.xml --tb=short
python -m ruff check src tests
python -m ruff format --check src tests
```

测试目录由本轮创建，验收后清理；JUnit 报告作为正式验证证据保留。新增专项测试分布在 `test_repair_learning.py`、`test_repair_regressions.py`、`test_repair_state_recovery.py`、`test_readiness_scopes.py`。独立审查复现的删记录误闭环、恢复绕过、旧 hash 状态、模块常量越界和跨表日期污染均已修正并纳入回归。

离线回归关注空 GZK 不入队、平台本地短路、真实本机执行后的空提取修复、日期保护与未知日期告警、单位差异放过、函数范围/字段回归、成功记忆晋升与隔离、数据库不可用降级等工程行为。受控模型回复测试可以验证链路是否按契约运行，但不能证明真实模型面对所有业务文件的准确率。

后续要评估更高业务准确率，需要固定、可复查的真实样本集及人工基准：覆盖原始 XLS 数值型年份、复杂多层表头、多 Sheet、多期间、单位冲突、真无数据、日期未知和 GZK 未覆盖等情况；分别记录首次成功率、有限修复后成功率、误放过/误拒绝、正确字段被改坏的回归率和超时比例。还需将平台实际 `excel_data → out_data` 结果与本机估计对照，区分规则覆盖、换算、执行部署和解析逻辑问题。

每次修复应在固定样本上复验源值、单位、统计期和名称层级；不能只看记录变多、GZK 命中变多或测试全绿。工程离线通过、记忆中有成功案例、`ready` 和 `downstream_readiness=READY`，都不能单独替代用户亲自测试工作流后确认最终结果正确这一阶段验收标准。
